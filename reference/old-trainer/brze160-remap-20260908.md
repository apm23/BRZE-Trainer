# BRZE 1.60 remap findings — 2026-09-08

This note records current-version mappings derived by comparing the exact unpacked legacy trainer with the supplied BRZE 1.60 executable. Runtime proof is called out separately from static proof.

## Native selected-unit list (static-proven; selection flags already runtime-proven)

Current selection list object: absolute VA `0x841708`, RVA `0x441708`.

Container layout decoded from the game's own list routines:
- `+0x00` head node pointer
- `+0x04` tail node pointer
- `+0x18` selected count

Node layout:
- `+0x00` next node
- `+0x04` previous node
- `+0x08` unit pointer

The game appends selected units at `0x5A70B7` via `ecx=0x841708; call 0x4ACB59`, then sets unit `+0x3A8=1`. Deselect removes the unit from the same list via `0x4AC124`. Deselect-all walks the same list with `0x4AC097` / `0x4C299A`.

This is the preferred F5/F6 top-up source. It avoids scanning all 2000 unit slots. Keep the event-driven HP/stamina delta hooks, but use this list only for the slow recovery/top-up path.

## Current selected-building pointer

Global absolute VA `0x8417D8`, RVA `0x4417D8`, is a current selected/focused building pointer. `0x5A7516` validates the building, checks owner at `+0x84` against local player ID `0x8416D0`, stores it to `0x8417D8`, and sets building `+0x51C=1`. Clear path at `0x5A757C` clears `+0x51C` and the global.

`0x8417D4` (RVA `0x4417D4`) is a second building-related current pointer; its clear path writes building `+0x518=0`. The old trainer also operated on two current-object globals, so these are strong candidates for the modern equivalent pair.

## Legacy Delete cheat -> current BRZE building fields

The old trainer performs 4-byte writes at deliberately unaligned addresses:
- object `+0x8E` <- `5000`
- object `+0x492` <- `100`
- object `+0x4BE` <- `100`

These are not ordinary independent DWORD fields. They write into the high 16 bits of the aligned fixed-point fields at `+0x8C`, `+0x490`, and `+0x4BC`.

Current BRZE still has the same aligned building fields:
- `+0x8C`
- `+0x490` (unit training progress)
- `+0x4BC` (another 16.16 progress channel)

Current code at `0x4D3A3C` adds to `building+0x4BC`, compares it against `0x00640000` (100.0), and sets `building+0x694=1` when complete. This strongly explains why the old trainer wrote integer 100 starting at `+0x4BE`: it forces the high word of the 16.16 progress value to 100.

Current code at `0x4D65DC` similarly reads `building+0x490`; completion threshold is `0x00640000`.

Therefore the legacy Delete technique is structurally preserved in BRZE 1.60 and is a strong candidate for F8 / instant research-upgrade testing on the current selected-building pointer(s). This is static-proven structure correspondence, not yet runtime-proven cheat behavior.

## F7 training

Current training routine `0x4D6573` stores the building pointer in ESI. At `0x4D65DC` it executes `add eax,[esi+0x490]`, stores to `+0x490` at `0x4D65E2`, then compares with `0x00640000`.

Latest legacy-pattern F7 hook targets `0x4D65DC` and writes `0x0064B540` to `[esi+0x490]` before executing the displaced instruction, gated by building owner `+0x84 == local player ID`. This mirrors the old trainer's F4 technique. It has not been runtime-tested because Windows Smart App Control blocked the fresh unsigned build.
